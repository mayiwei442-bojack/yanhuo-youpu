# 烟火有谱｜HTML Demo 调整与范围

## 1. 为什么需要简化

最终小程序方案包含 11 类页面、AI、小游戏、云同步和平台能力。当前目标是让评审或体验者在浏览器中完整走通核心价值，而不是提前完成正式小程序的全部工程。因此 HTML Demo 保留产品结构和接口，缩减平台依赖、远程服务和高成本互动。

## 2. 当前 Demo 的产品形态

- 入口仍为 `index.html`，内部采用移动端优先的响应式单页应用。
- 手机宽度呈现接近小程序的四栏底部导航；桌面端使用居中的移动应用画布或适度扩展的双栏布局。
- 可拆分 CSS、JavaScript 和数据文件，不要求把所有内容塞进一个巨型 HTML。
- 无构建工具也应能运行；如果数据使用 ES Module 或 fetch，必须同时提供明确的本地启动方式。
- 推荐优先把数据导出为普通脚本或内嵌 JSON，确保双击 `index.html` 也能演示。

## 3. 阶段一必须真实完成的页面

阶段一收敛为 8 个视图，不需要为每个状态制作独立 HTML 文件：

| 路由/视图 | 必须完成的内容 |
|---|---|
| `#/home` | 两个绝对主入口、少量推荐、最近状态 |
| `#/pantry` | 选择、搜索、分类、添加、删除食材；像素图反馈 |
| `#/recommendations` | 本地计算“马上能做/差 1–2 样/灵感推荐” |
| `#/recipes` | 90 道菜的搜索、分类和筛选；收藏可本地保存 |
| `#/recipe/:id` | 配料、已有/缺少、份数、步骤、安全提醒、采购和烹饪入口 |
| `#/shopping` | 生成、合并、勾选和保存采购项 |
| `#/cook/:id` | 可操作的分步图文教程、低/中/高火力、计时信息、进度恢复 |
| `#/me` | 收藏、最近浏览、饮食设置，以及阶段二/三的预览入口 |

两条闭环必须能完整走通：

1. 首页 → 食材篮 → 推荐结果 → 菜谱详情 → 图文烹饪。
2. 首页/菜谱库 → 菜谱详情 → 采购清单 → 勾选完成。

## 4. 阶段一的数据和算法简化

### 4.1 菜谱数据

使用现有 90 道菜，但先把 `tools/recipe_data.mjs` 转换为适合浏览器直接读取的结构。不要在浏览器端解析 Excel。

现有 ingredients 是分号分隔文本，开发前应预处理为结构化数组。至少增加：

- `id`
- `name`
- `category`（中餐/西餐/地域风味）
- `ingredients[]`（名称、数量、单位、是否核心）
- `steps[]`
- `imageThumb`
- `imageFull`
- `time`
- `difficulty`
- `allergens[]`

如果部分时间、难度、核心食材或过敏原数据尚未整理，阶段一可为演示用菜谱补齐合理的静态值，并在数据中标注 `demoEnriched: true`，不要假装这些字段来自原始数据库。

### 4.2 匹配算法

不调用 AI，使用可解释的本地规则：

1. 先根据用户设置排除明确过敏原冲突。
2. 统一食材别名，例如“西红柿/番茄”。
3. 计算核心食材缺失数量和全部食材覆盖率。
4. 核心食材不缺归为“马上能做”。
5. 核心食材缺少不超过 2 种归为“还差 1–2 样”。
6. 其余菜谱按覆盖率、时间和难度排序进入“换个灵感”。

推荐卡必须列出依据，例如“你已有番茄、鸡蛋和小葱，只需基础调味”。

### 4.3 状态保存

阶段一只使用 `localStorage` 保存食材篮、收藏、采购清单、饮食设置、最近浏览和烹饪进度。没有账户体系，也不上传数据。

## 5. 阶段二、三怎样“展示但不实现”

采用统一的“功能预览”交互，不做灰掉后毫无反馈的按钮，也不伪造成功结果。

| 预留功能 | 界面入口 | 点击后的表现 | 当前替代操作 |
|---|---|---|---|
| AI 自然语言录入 | 食材篮输入区 | 展示能力说明和示例输入 | “先手动选择食材” |
| AI 照片识别 | 添加食材面板 | 展示照片识别流程示意 | “从食材库选择” |
| AI 推荐解释 | 推荐卡“为什么推荐” | 可展示本地规则解释，并注明 AI 深度解释待接入 | 继续使用规则解释 |
| AI 替换建议 | 菜谱详情配料区 | 展示未来返回的四类建议结构 | 查看预置的基础替换说明或返回 |
| 抖音搜索 | 开始烹饪方式选择 | 展示生成的搜索词；能安全跳转则跳转，否则复制 | 复制“菜名 + 家常做法” |
| 烹饪小游戏 | 开始烹饪方式选择 | 进入完整视觉预览页，展示锅灶、托盘、三档火力和提示气泡 | “改用图文教程” |
| 云同步/登录 | 我的 | 展示未来同步内容和隐私说明 | “继续仅保存在本机” |
| 分享 | 采购清单/菜谱详情 | 展示未来分享卡片预览 | 浏览器支持时复制文本 |

预览弹层统一包含：功能名称、阶段标签、未来能做什么、当前为什么未开放、可用替代操作。推荐文案：

> 功能预览｜AI 食材识别将在下一阶段接入。当前 Demo 不会上传你的照片，你可以先从食材库手动选择。

## 6. 视觉方案的 HTML 调整

继续使用“现代东方菜谱册 × 数字灶台”，但降低不必要的实现成本：

- 菜谱列表使用 `assets/dishes/thumbnails/`，90 张合计约 1.26 MB。
- 详情按需加载 `assets/dishes/ai/` 原图；弱网或加载失败时回退缩略图。
- 像素图统一使用 `image-rendering: pixelated`，避免浏览器插值模糊。
- 只做一组高质量主转场：食材落入篮子 → 蒸汽 → 推荐纸条展开。
- 其余动效以 150–300ms 的反馈为主，并支持 `prefers-reduced-motion`。
- 标题可以使用有东方编辑感的本地/网络字体，正文必须保证中文清晰；字体失败时有可靠回退。

## 7. 当前不做的内容

- 不接真实大模型、视觉识别或语音服务。
- 不申请相机、麦克风、微信登录等权限。
- 不开发真实烹饪小游戏交互和评分逻辑。
- 不开发云数据库、多端同步、社交关系或运营后台。
- 不做正式小程序分包、审核、隐私弹窗和发布流程。
- 不补写未经核验的非遗名录结论；五道指定菜先用“地域风味/技艺故事预览”。

## 8. 从 HTML 迁移到小程序时要保留的边界

阶段一代码应拆成四层：

1. 数据仓库：读取菜谱和食材。
2. 业务服务：匹配、采购清单、安全规则、烹饪进度。
3. 状态与能力适配：localStorage、导航、文件选择、分享。
4. 界面组件：页面、卡片、弹层和反馈。

迁移小程序时主要替换第 3、4 层，前两层尽量复用。不要把匹配算法、DOM 操作和 localStorage 写进同一个大函数。
